# 技术文档 · 架构设计（第六棒）

**版本** 1.0.4 ｜ **阶段** 6 ｜ **上游** database-designer ｜ **下游** software-developer ｜ **运行时依赖** 无（纯文档撰写 + 一个标准库校验脚本）

## 1. 定位

在流水线中承担"把需求与数据结构翻译成代码骨架"的职责。它输出的是**约束**，不是实现：分层、模块边界、依赖方向、扩展点、命名规则。第七棒按这些约束铺目录与写代码。

## 2. 输入契约

| 必需上游产物 | 用途 | 缺失后果 |
|---|---|---|
| `02-requirement-review.md`，结论 YES | 证明需求可执行 | 门禁不通过，不得开工 |
| `01-prd.md`，含 FR 编号清单 | 模块划分与扩展点的依据 | 模块边界只能靠猜 |
| `05-database-design.md` 已定稿 | 数据访问层的划分依据 | 持久化层设计必然返工 |

**门禁规则**：缺任一项即停止，不产出 `06-architecture-design.md`。这是纯前置确认，不写"打回报告"。

## 3. 输出契约

- **文件名**：`06-architecture-design.md`（固定，下游按此名取件）
- **六节结构**：架构总览 / 分层架构 / 模块划分 / 技术选型 / 扩展性设计 / 约束与约定
- **必备表格**：分层表（层·职责·依赖的下层·关键组件）、模块表（模块·职责·对外接口·依赖模块）、选型表（关注点·选型·理由）
- **可照改样例**：`examples/06-architecture-design.example.md`，实测 `check_architecture.py` 退 0

## 4. 校验器行为（`scripts/check_architecture.py`）

判定逻辑（按源码顺序）：

1. 文件不存在 → 3；缺参数 → 2
2. `分层|架构` 无命中 → 记 FAIL（缺分层）
3. `模块` 无命中 → 记 FAIL（缺模块）
4. `扩展|演进` 无命中 → 记 FAIL（缺扩展性）
5. 占位符命中（`[...]{2,}` 除 `[^1]`、`【...】`、剥离合法尖括号后的 `<...>`）→ 先判 2，优先级高于 FAIL
6. 有 FAIL → 1；否则 → 0

**已做防误报**：`<div>`、`Map<String, Object>`、自动链接、脚注 `[^1]` 不会被判占位。

### 已知限制

| 限制 | 后果 | 缓解 |
|---|---|---|
| 只查三个关键词是否出现 | 一句话糊弄也能过；六节标题缺失不报 | 人工按 SKILL.md 的六节结构核对 |
| 不校验依赖方向是否真的向下 | 写了"上层依赖下层"但表格写反了，仍退 0 | 第七棒按此铺目录时会暴露 |
| 不校验模块表是否为空 | 有空表也能过 | 靠下游开发实际使用检验 |
| 占位符判定优先于缺项判定 | 同时存在时只报 2，不报缺项 | 先清占位再重跑 |

**定位**：结构闸门，不是质量闸门。它能拦住"忘了写扩展性"，拦不住"扩展性写得空洞"。

## 5. 运行环境

- Python ≥ 3.9，仅标准库（`re` / `sys` / `pathlib`）
- 跨平台，产物路径从 CWD 解析，可传绝对路径
- 脚本与产物路径**各自独立解析**：整套部署时 CWD 在仓库根；单棒独立时 CWD 在本目录

## 6. 能力边界

**能做**：分层划分、模块边界、技术选型（含理由）、扩展点定义、目录与命名约束。

**不能做**：写业务代码、画界面、设计数据库表（属第五棒）、判断选型在特定团队/预算下是否现实、微服务拆分。

**边界判据**：本棒输出的是"代码应该怎么组织"，第七棒输出的是"代码本身"。

## 7. 设计取舍

| 选择 | 为什么不选另一条路 |
|---|---|
| 六节固定结构 | 自由结构无法被脚本校验，下游也取不到字段 |
| 只查三个关键词 | 语义判定必然误报；误报会导致使用者绕过门禁 |
| 把"扩展性"设为必检项 | 这是最容易被跳过、代价又最高的一节（做错的架构都在这一步偷懒） |
| 门禁要求上游三件齐备 | 允许"边设计边补"会退化成猜，返工成本高于等待 |
| 默认分层单体 | 中小型项目上微服务的运维成本远超收益 |

## 8. 优缺点

**优点**

- 零依赖，单文件可跑，成本几乎为零；
- 把"架构"从口头讨论变成可交付、可校验的文件；
- 扩展点要求具体到接口，避免"预留空间"式空话；
- 六节结构对下游友好，开发可直接按表铺目录。

**缺点与缓解**

| 缺点 | 影响 | 缓解 |
|---|---|---|
| 校验宽松，形式合规≠质量合格 | 空洞架构能过门禁 | 用 ADR 模板补决策理由；评审时看扩展点是否具体 |
| 强制等待上游三件 | 快速原型场景显得慢 | 小项目可跳过本棒，直接在 `07-source/` 里写 README 说明架构 |
| 默认分层单体 | 不适用于微服务/嵌入式 | 明确写"不适用"，别硬套 |
| 不校验依赖方向正确性 | 表格写反不会被发现 | 开发铺目录时若发现循环依赖，回改本节 |

## 9. 失败模式与处置

| 现象 | 根因 | 处置 |
|---|---|---|
| 退 2 但找不到占位符 | 正文有 `【】` 或"待定"以外的未闭合尖括号 | 脚本会打印命中类型与前 3 处原文 |
| 退 1 说缺扩展性 | 只写了"扩展性设计"标题没写内容 | 补"新增功能怎么加 / 数据模型怎么演进"两条具体路径 |
| 连续 3 次同项失败 | 判据与产物长期不匹配 | 出《门禁阻塞报告》：失败项原文、已试三次修改、误报还是缺陷、三个选项（放宽判据/人工补/标记风险放行） |
| 文档越改越乱 | 整篇重生成 | 定点修补：只重写失败项所在小节 |

**禁止**：为让退出码变 0 而改校验脚本或改写失败项文字。

## 10. 与相邻技能的职责交界

| 邻棒 | 交界线 |
|---|---|
| database-designer（05） | 05 定表结构与关联；06 只按它划持久化层，不改表 |
