# 新手手册 · 架构设计（第六棒）

> 这一棒不写代码，只决定**代码怎么组织**。做对了，以后加功能是"新增一个模块"；做错了，是"改五个文件还不知道会不会崩"。

## 一、它在流水线的哪个位置

```
01 需求 → 02 评审 → 03 原型 → 04 UI → 05 数据库 → 【06 架构】 → 07 开发 → 08 测试 → 09 安全
```

它吃两样东西（`01-prd.md` 的 FR 清单、`05-database-design.md`），吐一样东西（`06-architecture-design.md`），第七棒的开发照着它铺目录。

## 二、为什么不能"边写边想架构"

| 省掉这一步 | 三个月后会怎样 |
|---|---|
| 没定分层 | 业务逻辑和 SQL 混在一个文件，换数据库要动全部代码 |
| 没定模块边界 | 两个模块互相读对方的表，改一处崩两处 |
| 没留扩展点 | 加个"到期提醒"要动五个既有文件，还得回归全部功能 |
| 没写选型理由 | 没人敢换，也没人知道当初为什么选它；换人接手就重来一遍 |

**架构文档的真正读者不是评委，是三个月后的你和接手的开发。**

## 三、开工前必须先确认三件事

技能的第 0 步是门禁，不是建议：

1. `02-requirement-review.md` 结论是 **YES**；
2. `01-prd.md` 有 FR 编号清单；
3. `05-database-design.md` 已定稿。

**缺一项就停下**。没有数据库设计去定持久化层，等于猜；猜出来的架构第七棒一定会推翻。

## 四、具体怎么做（六步）

1. **读透前两份产物**：系统要做什么、数据怎么存。
2. **定分层**：表现层 / 接口层 / 业务逻辑层 / 数据访问层 / 基础设施层，每层一句话职责，**依赖方向固定向下**。
3. **定模块**：按业务域拆（任务、清单、用户…），每个模块写清边界、对外接口、依赖谁。模块间只走接口。
4. **定选型**：按 PRD 的非功能需求选（性能、并发、部署形态），每条写一句理由。**不追流行，追够用且好扩展。**
5. **画扩展点**：加新功能挂哪里、扩展接口定义在哪、数据模型怎么演进。
6. **写约束**：目录结构、命名、依赖规则——这些是第七棒必须遵守的硬约定。

## 五、怎么知道写完了

```bash
python scripts/check_architecture.py 06-architecture-design.md; echo "EXIT=$?"
```

| 退出码 | 含义 | 动作 |
|---|---|---|
| 0 | 通过 | 交稿 |
| 1 | 缺分层 / 缺模块 / 缺扩展性 | 补对应小节，重跑 |
| 2 | 有占位残留 | 把 `【待定】` 之类换成真内容，重跑 |
| 3 | 文件不存在 | 检查文件名与路径 |

⚠️ 不要用 `python x.py | tail` 取退出码，那拿到的是 `tail` 的码，永远 0。

## 六、新手最常犯的四个错

1. **把架构文档写成技术栈清单**。"用了 Vue + FastAPI + MySQL"不是架构，是采购单。架构说的是**层次、边界、依赖方向**。
2. **模块划分按技术分而不是按业务分**。`controllers/`、`services/` 是层，不是模块；模块应该是 `task/`、`list/`、`user/`。
3. **扩展性写空话**。"预留扩展空间"等于没写。要写"新增提醒通道：实现 NotifyChannel 接口，不改既有代码"。
4. **一次画到最终形态**。第一版只覆盖当前 PRD 的功能，把未来需求塞进架构会让第一版做不完。

## 七、它做不到什么

- **不判断选型对错**。它要求你写清理由和代价，判断仍靠你的约束。
- **不适用于所有项目形态**。分层单体这套判据在嵌入式、算法库、数据脚本上基本失效。
- **不给微服务拆分方案**。默认形态是分层单体。

## 八、记住三句话

1. 第 0 步是门禁，缺文档不动手。
2. 写层次、边界、依赖方向，不写采购清单。
3. 扩展点要具体到"实现哪个接口"，不是"预留空间"。
