# 架构决策记录（ADR）模板

每次做**不可逆或代价高的技术选择**时补一份，编号递增，写完不删（要推翻就新写一份，并注明取代了哪一条）。判断标准：这个决定如果半年后被人问"当初为什么这么选"，你需要一个比"当时觉得挺好"更硬的答案。

---

## ADR-001 标题（用一句话说清选了什么）

- **日期**：2026-11-03
- **状态**：提议 / 已采纳 / 已废弃 / 被 ADR-00X 取代
- **决策者**：

### 背景

当时面对什么问题？有哪些约束（时间、人力、既有技术栈、合规）？**只写事实，不写倾向。**

### 备选方案

| 方案 | 优点 | 缺点 | 放弃原因 |
|---|---|---|---|
| A | | | |
| B | | | |
| C | | | |

至少列三个。**只列一个方案等于没做决策**，是通知。

### 决策

选了哪个，一句话。

### 理由

为什么是它、不是别的。写清**关键判据**（哪条约束起决定作用），不要写"综合考虑"。

### 后果

- 好的后果：得到了什么。
- 坏的后果：**主动写下你接受的代价**，例如"放弃了水平扩展能力""本机开发环境与生产不一致"。
- 触发重审的条件：出现什么情况时这条决策需要重开（例如"日活超过 1 万"“需要多租户”）。

---

## 什么时候一定要写

1. 选了数据库 / 存储形态；
2. 定了分层与模块边界（后续开发都会受它约束）；
3. 引入或拒绝一个重依赖（框架、消息队列、第三方服务）；
4. 做了"明知不完美但先这样"的妥协（**这条最值得写**，不写就会在半年后被当成疏漏重犯）。
